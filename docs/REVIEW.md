# v0.6.46 · v0.6.45 리뷰 P1: 재적용이 배열 위치를 기억하던 문제

기준: v0.6.45 `916b3ce`.

- `diffPaths`: id가 있는 목록(장면·구간·엔티티·기록)은 위치 대신 id로 — 경로 조각 `{ id }`, 추가 `{ add, after: <앞 항목 id|null> }`, 삭제 `{ remove: id }`. id가 없는 목록(포인트 등)은 `{ i, len }`(그 편집이 본 길이일 때만 같은 칸). 길이가 달라진 id 없는 목록, 원시값 배열의 변경, 최상위 교체는 `unsafe` → 재적용 불가.
- `applyPaths`: 'changed' / 'same' / 'stop'. 대상 id가 없거나, 목록 길이가 달라졌거나, 부모가 없으면 **만들지 않고** 'stop'. 추가할 id가 이미 있거나 `after` 항목이 없으면 'stop'. 삭제 대상이 이미 없으면 그대로(이미 그 상태).
- 재적용 함수: 사본에 적용 → 'stop'이면 예외(그 변경은 같은 오류로 취소), 'same'이면 변경 없음으로 완료 처리(오류 아님), 'changed'면 `cleanMem(clone(next))` 통과한 경우에만 실제 기억에 반영.
- 재현 3건: A 삭제 실패 + B 📌 → B만 고정·A 복원 / A 📌 실패 + B 삭제 → A 고정 안 살아남·B 삭제 / 추가 실패 + 그 항목 📌 → 📌 취소, `[]` 생성 없음, 파일 형식 유지.

검사: Node 375개, 브라우저 23묶음 통과. `quests.cjs` 15–17(위 세 경우, 화면 = 파일).

# v0.6.45 · v0.6.44 리뷰 3건 + 번역 버튼 크기

2. [P2] 미확정 변경이 섞이는 문제: 쓰기는 그 순간 페이지에 있는 메모리 전체를 저장하므로, 쓰기 시작 시점의 대기 항목(`covered`)을 그 쓰기로 함께 **확정**(`done`)하고 대기열에서 뺌. 확정된 항목의 차례가 오면 쓰지 않고 성공 처리. 그래서 "앞 두 저장 성공·마지막만 실패"는 생기지 않음(마지막 변경은 이미 둘째 쓰기에 담겨 확정). 쓰기가 실패하면 그 쓰기에 담긴 것과 뒤의 것까지 모두 되돌리고 버튼 편집만 다시 적용(v0.6.44와 같음) → 다시 적용한 것은 자기 차례에 새로 씀. 파일 = 마지막으로 성공한 쓰기 시점의 화면.
3. [P2] 재적용 값: 버튼 편집(`replay`)은 처음 적용할 때 `diffPaths(prev.mem, after.mem)`로 바뀐 경로와 최종 값을 기억(`entry.patch`). 재적용은 함수 재실행이 아니라 `applyPaths`(그 경로를 최종 값으로 설정, 같으면 변경 없음). ○→●→○에서 첫 쓰기 실패 → ○ 유지. 같은 장면의 다른 포인트를 바꾼 경우에도 실패한 변경이 되살아나지 않음(경로 단위). 길이가 바뀐 배열은 배열 전체가 값.
- 번역 버튼: `.sp-langwrap`이 넓은 화면에서도 `flex: 1 1 auto`라 남는 폭을 모두 차지 → 기본 `0 1 auto`, 560px 이하에서만 늘어남(다른 버튼과 같음). 스토리 콘솔의 `LANGUAGE` 꼬리표가 넓은 화면의 "꼬리표 없음" 규칙보다 우선해 `번역LANGUAGE`로 붙던 것 삭제. 16개 스킨 × 1100/393px × 번역/원문(+N) 확인.

검사: Node 375개, 브라우저 23묶음 통과. `quests.cjs` 12(○→●→○ 첫 쓰기 실패), 13(●·📌·★ 연속 + 실패 주입 → 화면 = 파일), 14(방 이동 뒤 대기 저장은 새 방에 쓰지 않고 오류).

참고: 실제 실리태번 `saveMetadata`는 대부분의 서버 실패를 스스로 잡고 정상 반환해서(이 확장은 감지 못 함), 이 경로는 예외를 던지는 실패에만 해당.

# v0.6.44 · 연속 저장 중 앞선 실패가 뒤의 변경을 되돌리던 문제

기준: v0.6.43 `1368316`.

- [P2] `transact`를 방(roomKey|epoch)별 저장 대기열로: 변경은 바로 화면에 적용(`applyEntry`: 이전 상태·하이드 스냅샷, change, undo/rev, syncHide, 주입, render), 쓰기(`writeEntry`)는 대기열 순서대로 하나씩.
- 쓰기 실패 시: 그 변경과 뒤에 쌓인 변경을 역순으로 각자의 "이전 상태"로 되돌림(`restoreEntry`, 메타데이터는 적용 당시 방의 객체 `entry.meta` — 방을 옮긴 뒤에도 새 방을 건드리지 않음). 그다음 뒤의 변경 중 `replay: true`(버튼 편집 `commitEdit`)이고 같은 방이면 다시 적용해 대기열에 남기고 자기 차례에 저장. 다시 적용할 수 없는 것(저장 실행 중의 기록 등, 하이드 재계산 포함)은 같은 오류로 취소. 실패한 변경의 오류 문구에 "그 뒤에 한 변경 N개는 다시 적용해 저장해요" 추가.
- 순서대로 쓰므로 뒤의 쓰기가 실패한 변경을 담아 먼저 성공하는 일이 없음(파일과 화면이 갈라지지 않음).
- ★ 다시 적용은 버튼 편집의 함수(현재 기억에서 다시 계산)를 다시 실행하는 것이라, 토글(📌, ★)은 "뒤집기"가 다시 일어남 — 실패한 변경이 되돌려진 뒤 그 위에서 다시 뒤집으므로 사용자가 본 결과와 같음(실패한 변경이 같은 항목을 바꾼 경우만 다를 수 있음: 같은 📌를 두 번 누른 경우 등).

검사: Node 375개, 브라우저 23묶음 통과. `quests.cjs` 11(첫 쓰기 600ms 뒤 실패 + 그사이 📌 → 📌 유지·대기/제외 변경만 취소·파일과 화면 같음). 모의 저장에 `M.failOnce`.

- `upgradeStoryTimes`: 저장된 주장을 현재 규칙으로 다시 계산(recomputeStoryTimes). 바뀐 경우에만 저장 예약. index.js state()에서 기억 객체마다 한 번, 실행 중이 아닐 때만. 직접 지정과 삭제된 앞부분의 경계 보존은 recompute 규칙을 따름.
- 수집 지침: 인포박스 줄은 explicit로, 날짜가 같아도 보고하도록 한 줄 추가.
- 화면: 장면 시간 줄에 ✎. 첫 미확인 가장자리(없으면 마지막 끝)의 편집 창을 열고 구간 목록을 펼침.

## 루팅 반영 실패 이유 (loot.js, index.js)
- `attachLoot`가 연결 못 한 id마다 `evidence`(포인트에 붙였지만 그 메시지를 근거로 안 적음) / `unlinked`(어디에도 안 붙임)를 반환(`used.why`). 수집 데이터에는 열거되지 않는 속성으로 보관해 검사·저장에 섞이지 않음.
- `settleLoot`는 이유 문장으로 `반영 실패 · …`을 남기고 `fails`를 셈. 응답에는 연결됐는데 저장 후 없으면 "검사에서 빠졌어요". 요청 오류·장면 없음도 같은 `failLoot` 경로.
- 대기열 카드: 이유, 2번째 이상 실패 횟수, 다음 세이브 재시도 안내(원문이 바뀐 항목 제외). 알림: 첫 이유 + 재시도 안내. 결과 복사: `[루팅 반영 실패 N개]` 항목별. 결과 복사 버튼은 반영 실패가 있어도 보임. 연결 규칙(근거 번호 일치)은 그대로.

## v0.6.4 · 2단계 약속·빚 기한, 대략 표현 차단

기준 커밋: b27215b6acf44740182e9648dfa68b4b3bd3c5dd (v0.6.3). 연표·시작 날짜 지정·실패 응답 임시 보관은 3단계로 남김.

대략 표현 수정 (v0.6.3 리뷰 후속):
- `temporal.js readElapsed`가 쯤/정도/가량/남짓/얼추/거의/안팎, 단위 뒤 넘게/이상/이내/여, nearly/almost/around/more than/less than/or so/over·under+수량을 만나면 일 수를 읽지 않음(null). `advanceQuoteMatches`는 읽은 일 수가 정확히 하나이고 응답과 같을 때만 통과. `다음 날 밤과 그다음 날`처럼 두 단계가 보이면 확정하지 않음.

기한 동작:
- 수집 응답 `add`의 `due {expr, days, date, msg}`: expr은 해당 메시지에 글자 그대로 있어야 저장. days는 `dueDaysMatch`(내일 1, 모레 2, 글피 3, 오늘/오늘 밤 0, 숫자 경과 표현)와 맞을 때만, date는 expr 안에 있을 때만 남김. 내일모레·며칠 안에·이번 주말은 표현만 보존.
- 위치는 저장하지 않고 매번 계산: 말한 구간(msg가 속한 구간)이 회상이 아니고 시작·끝이 같은 날로 확인될 때만 기준일 + days. 그래서 구간 시간을 고치면 기한도 따라감.
- 상태 left/today/past는 같은 기준점끼리 일 수, 다르면 실제 날짜끼리 비교. 둘 다 안 되면 `확인 필요`. `기한 지남`은 상태(open)를 바꾸지 않으며 화면·주입 모두 "마지막 기록 기준, 어겼다는 뜻 아님"을 붙임. 완료/실패한 약속은 표현만 표시.
- `setManualDue`: 지금 시간이 확인된 경우만 허용. `YYYY-MM-DD`(지금 기준에 실제 날짜가 있을 때) 또는 N일째. 직접 지정은 AI update가 덮지 않고, 내보내기·방 이동·되돌리기에서 유지되며 빈 값으로 해제됨. update의 due 교체는 manual이 없을 때만.

집중 재검토 지점: `temporal.js`의 `resolveDueClaim`, `madeAt`, `dueStamp`, `dueStatus`, `setManualDue`; `core.js applyResult`의 add/update due 처리와 `cleanMem`; `index.js saveEdit`의 사전 검증(복제본에 먼저 적용).

검증: Node 245개 통과(tests/deadline.test.mjs 9개 신설), 브라우저 13개 묶음 전체 통과(신규 deadline.cjs 포함). 실제 모델 호출은 하지 않음.

다음 실제 모델 확인: "내일 만나자" → 다음 날 → 이틀 뒤(기한 지남 표시와 퀘스트 진행 중 유지), "며칠 안에 갚을게"(표현만), "모레까지"(+2), "일주일쯤 뒤"(시간 미확인), 기한 뒤 "몇 주 뒤" 점프(확인 필요). 모델이 days를 직접 계산하거나 날짜를 지어내는지 응답 원문과 함께 볼 것.
