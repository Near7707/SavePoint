# 계획 · v0.7.0 기억 저장 분리 (확정, v0.6.64에서 0단계 시작)

0단계(v0.6.64)에서 코드로 옮기며 정한 세부와 계획에 없던 것은 [REVIEW.md](REVIEW.md) v0.6.64의 ★에 있어요. 코드는 `home.js`.

**왜:** 실리태번이 자기 타이밍에 화면 전체를 저장하는 것과의 경쟁(구조 리뷰 P1·P2-3)을 기억 쪽에서 없애기. 직접 채팅 쓰기·화면 기준 자동 재저장은 보류(새 답변·다른 기기 삭제를 덮을 수 있음). 원칙: **서버와 화면이 다르거나 저장 여부가 불명확하면 쓰기를 멈추고, 방을 다시 연 뒤 판단.**

## 무엇이 어디로
| 묶음 | 기능 | 쓰는 곳 |
|---|---|---|
| A. 기억만 | 버튼 편집(★⚓●✎🗑), 퀘스트·보관함·파티, 루팅, 기록 확인 결과, 체크포인트 결과 표시, 번역, 주입 다시 고르기, 슬롯 연결, 예전 형식 정리 | 기억 파일만 (**채팅 저장 0회**) |
| B. 기억 + 숨김 | 체크포인트·퀵세이브·장면 닫기(자동 하이드), 리와인드, 리셋, 같은 방 불러오기, 원문 변경 감지, 👻 수동 하이드 | 기억 파일 + 채팅의 숨김 표시 |
| C. 원문 | 새 방 이어하기 #0 | 채팅 파일 |
- **🔖는 이번에는 메시지에 붙여 둠**(채팅 파일, 숨김과 같은 수준). 🔖 고치기(`repairKeep`)도 지금처럼.
- 채팅 파일 속 예전 기억 사본은 **지우지 않음**(1단계 채팅 저장 0회). 이후 SavePoint는 그 키를 건드리지 않음.

## 파일 (모두 `user/files`, 채팅 파일에는 아무것도 안 씀)
- `mem-<기억ID>`: 기억 + 번호(rev) + 영수증(wid) + 최근 몇 번의 (rev, wid) 목록 + 출처(이전/분기/새 방) + home(방 주소·고유값) + (v0.6.65) 연결할 때 채팅에 있던 예전 사본 해시.
- `room-<방 주소 해시>`: **방 이름표.** 방 주소 = **캐릭터(또는 그룹) 범위 + 채팅 파일 이름**(안에 전체를 적고 읽을 때 대조), 고유값, 기억ID, 원문 지문 몇 개, 상태(`연결`/`이름 바뀜 → 새 주소`).
- `int-<고유값 해시>`: 그 고유값을 가진 방 주소 **목록**. **검색 단서일 뿐, 이것만으로 연결하지 않음**(가져오기·복사본은 같은 값).
- `moved-<원본 방 주소 + 예전 사본 해시>`: **이전 완료 표시.** 옮긴 기억ID, 옮길 때의 번호. 해시만으로 공유하지 않음.
- (v0.6.65) `moving-<방 주소 해시>`: **이전 시작 표시.** 시작할 때의 예전 사본 해시, 기억ID, 영수증. 방 주소만으로 찾으므로 이전 도중 사본이 바뀌어도 이전 시도를 찾음.
- (v0.6.65) `copy-<예전 사본 해시>`: 그 사본을 옮긴 방 목록. **보류에만 씀, 연결에는 안 씀**(고유값 없는 옛 채팅을 다른 기기에서 이름 바꾼 경우의 중복 이전 막기).
- **기억ID는 정해진 규칙으로**: 이전 = hash(방 주소 + 사본 해시), 분기·새 방 = hash(방 주소 + 고유값). 재시도가 같은 파일을 가리키고, **이름표가 없어도 이름으로 그 방 기억 파일을 찾을 수 있음.**
- **파일 읽기는 네 가지로 구분**(새 함수): 없음(서버가 없다고 답함) / 손상(파싱 실패) / 오류 / 정상. 손상·오류는 절대 "없음"으로 보지 않고 새로 만들거나 덮지 않음.

## 방 열기 판정 순서 (위에서 처음 맞는 줄에서 멈춤)
0. 필요한 파일 중 손상·오류가 있음 → **읽기 실패**(멈춤, 다시 확인만)

이름표가 있을 때
1. 고유값이 둘 다 있는데 다름 → **보류**
2. 채팅 속 예전 사본이 이전 기록과 다름(구버전 기기가 다시 씀) → **보류**, 합치지 않음
3. 같은 방 증명: 고유값 둘 다 같음 / (고유값 없음 또는 이름표에만 없음) 예전 사본 해시가 이전 기록과 같음 / 이름표엔 있고 파일엔 없음 → 보류 / 증명 안 되면 **보류**. (v0.6.69) **지문 일치는 증명이 아님**(같은 이름·같은 첫 인사말로 새로 만든 방도 지문이 같음) → 지문만 맞으면 보류, 지문 비교 결과는 보류 이유와 함께 넘김.
4. 같은 방 확인 뒤에만: 지문 일부 다름 → 연결 + 원문 변경 처리

이름표가 없을 때
5. 이 기기에서 확인된 이름 변경(`CHAT_RENAMED`, 실패하면 이 기기 설정에 적어 두고 다음에 재시도) + 고유값 일치 → 이름표 옮기기(옛 이름표는 `이름 바뀜`으로 남김). **원래 이름이 목록에서 사라진 것만으로는 이름 변경으로 보지 않음**(원본 삭제 후 가져오기와 구분 불가).
6. **기존 연결 복구(분기 판정보다 먼저)**: 이 방 주소로 정해지는 기억ID의 파일(또는 이 방을 가리키는 고유값 단서·이전 완료 표시·이전 시작 표시)이 있고, 그 파일이 정상이고 home(주소·고유값)이 이 방과 같으면 → **그 방의 최신 기억에 이름표만 다시 연결**. 손상·오류면 멈춤. (v0.6.65) 기억 파일에 적힌 예전 사본이나 이전 시작 표시의 사본이 지금 채팅의 사본과 다르면 **보류**. 시작 표시만 있고 본체가 없으면: 같은 사본이면 10번으로 다시 이전, 채팅에 사본이 없으면 보류. (v0.6.67) 찾은 본체에 고유값이 없으면 주소만으로는 연결하지 않음: (v0.6.69) 예전 사본이 같아야 함(지문 일치는 증명 아님), 아니면 **보류**(이름 재사용한 새 방, 기존 기억 파일은 그대로). (v0.6.69) 찾은 본체가 **이전으로 만든 것**(이름표 없음 = 끝나지 않은 이전)이고 그 사본을 다른 방이 이미 옮긴 기록(다른 방의 이전 완료 표시, `copy-` 단서)이 있으면 **보류** — 쓰기 재시도(`writePlan`·`writeCopy`)와 같은 결론. 분기로 만든 본체는 부모의 사본을 물려받으므로 이 확인을 하지 않음. 고유값이 둘 다 있고 다르면 사본이 같아도 보류(이름표 있음 1번, 없음 6번). (v0.6.71) **연결은 이름표만이 아님:** 이름표 없는 기억 파일 = 쓰기가 끝나기 전에 멈춘 것 → 남은 쓰기를 이어서(빠진 이전 완료 표시·`copy-`·`int-` 단서 먼저, 이름표 마지막, 본체는 안 씀, `relinkMemory`). 사본은 기억 파일에 적힌 것(채팅에서만 사라진 경우도 연결). 판정 때 본 기억 파일이 그대로(rev·영수증)일 때만 — 사라지거나 바뀌었으면 멈춤. `copy-` 단서는 본체를 읽은 뒤 새로 읽음.
8. (v0.6.65부터 7번보다 먼저) 같은 고유값이 다른 방에 연결돼 있음 → **보류**(후보로만 보여 줌). 연결된 분기방을 가져온 방이 부모 기억을 복사하지 않게. (v0.6.67) 그 방 이름표의 고유값이 지금도 같을 때만 후보. 이름표가 없으면 그 방 본체가 그 방(주소·이 고유값)에 있을 때 후보.
7. 분기 조건(고유값이 부모와 다름 + `main_chat`이 같은 범위의 연결된 방) → 분기 이어받기(아래). 근거 부족하면 **보류**.
9. 예전 사본이 다른 방에서 이미 옮긴 것과 같음(이전 완료 표시, 또는 `copy-` 단서에 다른 방) → **보류**
10. 예전 사본 있음 → **이전**
11. SavePoint 흔적(예전 사본, SavePoint 숨김 표시) 있음 → **보류**
12. 새 방. 고유값이 서버 파일에 생긴 뒤에만 기억을 만듦. 고유값 없는 옛 채팅은 같은 이름만으로 기존 기억을 붙이지 않음.
- 보류 중에는 어떤 파일도 쓰거나 지우지 않음.
- 0단계 검사: 각 줄 + "윗줄 조건도 같이 맞는 경우"(예: 고유값 다름 + 지문 일부 다름 → 1번 보류).

## 분기 이어받기
1. 부모 기억 파일을 읽어 **사본 위에서** 계산(부모 파일은 안 건드림).
2. 분기방 서버 파일 메시지와 부모 기억의 원문 지문을 비교해 처음 어긋나는 자리를 찾음.
3. 그 자리를 덮는 요약부터 되감음(`rollbackFrom`). 이력이 잘린 곳(`floor`)보다 앞이면 실패.
4. 되감은 결과의 기록된 지문이 **전부** 분기방과 일치해야 함.
5. (v0.6.67) 이력(`history`)이 없으면 되감기 불가로 봄. (v0.6.69) 되돌릴 수 없는 항목(빈 값, 차이 없음, 범위 없는 요약, (v0.6.71) 변경의 `before`·`after` 누락이나 순서 목록과 모순, 쓸 수 없는 `nextBefore`·`nextAfter`)이 있거나 되감기 중 오류가 나도 같음. 실패하면 부모 AUTO·QUICK 중 지문이 전부 맞는 것을 찾음. 없으면 **보류**. (v0.6.65) 되감고 남은 기록이 0개(첫 메시지부터 다름)도 실패로 봄(지문 0개는 증명 아님) → 맞는 슬롯, 없으면 보류. 빈 기억으로 시작할지는 사용자가 고름(v0.7.1 보류 화면).
6. 성공하면 새 기억ID로 저장, 되돌리기·검사 결과·슬롯 연결·실패 기록은 비움.
- 검사: 부모 #80 진행 뒤 #20 분기 / 분기 지점 마지막 스와이프 다름 / 이력 부족 ± 맞는 슬롯 / 부모 기억 못 읽음 / 부모가 앞쪽 원문 고침 / 첫 메시지부터 다름 / 분기의 분기 / 그룹 분기 / 실리태번 체크포인트 / **독립적으로 진행한 분기방에서 이름표만 없어짐 → 부모에서 다시 이어받지 않고 그 방의 최신 기억이 그대로 연결됨.**

## 이전과 재시도
- 처음 이전: 기억 파일이 있는지 먼저 확인 → 없으면 본체 → **다시 읽어 확인** → 이전 완료 표시 → 고유값 단서 → 이름표(마지막).
  - (v0.6.65) 실제 순서: 이전 시작 표시 → 다시 읽기 → 본체 → 다시 읽기 → 이전 완료 표시 → `copy-` 단서 → 고유값 단서 → 시작 표시 다시 읽기 → 이름표. 코드는 `home.js`의 `writePlan`·`placeMemory`.
  - (v0.6.67) 본체를 쓰기 바로 전에 다시 읽어, 이미 있으면 쓰지 않음(같은 방·같은 사본이면 그대로 받아들이고, 아니면 보류). 시작할 때와 `copy-` 단서를 고쳐 쓸 때 단서에 다른 방이 있으면 보류.
  - (v0.6.78) 이름표는 쓰기 바로 전에 다시 읽음: 없으면 씀, 같은 연결(같은 기억·고유값)이면 그대로, 다른 연결이나 `이름 바뀜`이면 **보류**(`tagChanged`), 못 읽으면 멈춤. 처음 이전과 연결 복구(`relinkMemory`) 모두.
  - (v0.6.82) "같은 연결"은 한 규칙(`sameLink`: `linked` · 같은 기억 · 같은 고유값 · **같은 예전 사본**)으로, 계획할 때와 이름표 직전 모두. 계획할 때 다른 이름표가 있어도 이제 멈춤(`tagDiff`)이 아니라 **보류**(`tagChanged`).
  - (v0.6.65) **동시 이전:** 본체를 다시 읽었을 때 영수증이 내 것이 아니면, 상대 파일이 정상이고 · 같은 방(주소·고유값)이고 · 같은 원본 사본에서 시작한 이전일 때만 상대 본체를 그대로 두고(다시 쓰지 않음) 연결을 마무리. 출처가 다르거나 불명확하면 **보류**. 시작 표시를 다시 읽었을 때 다른 사본의 표시면 **보류**.
  - (v0.6.65) **한계:** 서버에 "비교 후 쓰기"가 없어서, 한 기기가 시작 표시를 확인한 뒤에 다른 기기가 덮고 자기 표시를 확인하면 둘 다 통과할 수 있음. 이름표 직전의 다시 읽기가 대부분 잡지만 "동시에도 기억이 절대 둘로 갈라지지 않음"은 보장하지 않음. 검사 기준은 **"충돌을 발견하면 보류"**.
- **연결 복구와 본체 재작성 분리**: 기억 파일이 이미 있으면 본체는 절대 다시 쓰지 않음. 출처(원본 방·사본 해시)가 같으면 ~~이름표만~~ (v0.6.71) 빠진 단서를 채우고 이름표(번호가 더 새로워도 그대로 둠). 이전이면 이름표 직전에 `copy-` 단서를 다시 읽어 다른 방이 있으면 보류. 출처가 다르거나, 읽지 못하거나, 존재를 확인 못 하면 **멈춤**. 이전 완료 표시는 있는데 본체가 없으면 예전 사본으로 다시 만들지 않고 **보류**(슬롯 복구 안내).

## 저장 순서와 중간 실패 (규칙: "숨겨졌는데 기억에 없음"은 절대 남기지 않음)
- **자동 하이드:** 기억 파일 저장 → 성공 뒤에만 화면에 숨김 표시 → 채팅 저장. 기억 실패 = 아무것도 안 바뀜. 기억 불명 = 다시 읽어 판단, 모르면 그 방 쓰기 멈춤. 기억 OK·숨김 실패 = 기록과 원문이 둘 다 들어감(토큰만 더), 그대로 두고 안내.
- **리와인드·리셋·같은 방 불러오기:** 새 기억 미리 계산 → 더는 안 덮는 메시지 숨김 풀기 → 채팅 저장 → **다시 읽어 확인** → 기억 파일 저장 → (새로 덮은 게 있으면) 숨김. 해제 실패 = 화면 되돌림. 해제 불명 = 기억 안 바꾸고 멈춤. 기억 실패 = 원문 보임 + 예전 기억(겹침), 안내.
- **#0 이어하기:** ① 기억 파일에 "기억만 불러온 상태" + 연결 예정(새 #0 지문) → ② #0 교체 + `tainted` 채팅 저장 → 다시 읽기 → ③ 기억 파일에서 연결 확정. ① 실패 = 그대로. ② 실패 = 기억만 불러온 상태(⏪ 가능). ② 불명 = 멈춤, 나중에 #0 지문으로 판단. ③ 실패 = 다음 차례에 재확정, 끝내 못 하면 그 메시지가 한 번 더 기록될 수 있음(잃는 것은 없음).
- **방을 열 때는 채팅 저장 0회.** 숨김은 계산만: "보이는데 기억에 있음" → 그대로 두고 안내. "숨겨졌는데 기억에 없음" → 안내 + 자동 기록 멈춤. 방 열 때 원문 변경으로 되감아야 하면 표시만 하고 자동 기록 멈춤. `#0` 미확정은 서버 #0 지문으로 확정/취소(기억 파일만).
- **자동 기록 멈춤 조건:** 보류, 읽기 실패, 숨겨졌는데 기억에 없음, 분기로 복사된 숨김을 이어받은 기억이 못 덮음, `#0` 미확정, 원문 변경 되감기 대기. 다시 시작은 사용자가 `원문과 기억 맞추기`(위 순서, 이때는 채팅 저장 허용).
- 사용자가 메시지를 고쳤을 때의 원문 변경 감지는 지금처럼 바로(위 리와인드 순서).

## 답변 막기 (v0.7.0, c1~c2b 구현 · c3에서 지금 동작으로 고침)
> 처음 설계(시작 이벤트에서 띄움, 확인창 안 `다시 확인`·연결·복사·슬롯 버튼, 상태칸 이유 한 줄)는 c 설계·c2b에서 바뀌었어요. 아래가 지금 동작이고, 자세한 과정은 아래 "v0.7.0-c 설계"~"v0.7.0-c2b" 줄과 REVIEW.md.
- **묻는 기준:** 이번 생성에서 빠지는 SavePoint 숨김(`is_system` + `savepointHidden`) 중 브리핑을 만드는 기억(`liveState()`)의 기록 범위 밖이 있을 때만. 멈춘 이유 이름으로 나누지 않음(저장만 멈춘 방도 기억이 덮으면 통과). 브리핑 꺼짐·기억 없음·검토 = 범위 없음. 브리핑 예산의 압축·생략은 빠진 것 아님. 사용자 직접 숨김(표시 없음)은 안 봄. 정상 방은 묻지 않음.

## 그 뒤: 채팅 파일 쓰기를 단계적으로 줄이기 (v0.6.83 리뷰 뒤 정함)
**왜:** 같은 방 저장 경합(P1)이 반복된 뿌리는 SavePoint가 실리태번과 함께 채팅 파일을 통째로 쓰는 것. 서버에 "바뀌었으면 쓰지 않기"가 없어서, 확장이 할 수 있는 건 다시 읽어 추측하는 것뿐이라 순서마다 새 틈이 나옴. 쓰는 횟수와 종류를 줄이는 것이 근본 해결.
1. **기억 먼저 분리** — v0.7.0(위 계획 그대로). 이 단계 뒤에도 하이드·🔶·#0은 채팅 파일에 씀.
2. **하이드·🔶 옮기기 전 실제 실리태번 검증(실험판)** — 숨김·🔶 표시를 SavePoint 파일에 적고, 화면은 스타일로, AI 요청에서는 interceptor에서 원문을 빼는 방식. 옮기기 전에 실제 실리태번에서 확인: ① 실제 프롬프트(프롬프트 보기)에서 숨긴 원문만 빠짐 ② 채팅 파일이 그대로(SavePoint가 쓰지 않음, `is_system`이 바뀌지 않음) ③ 일반 전송·재생성·스와이프·이어쓰기·그룹 채팅·대신 쓰기(impersonate)에서 같은 결과 ④ 다른 확장과 함께. 통과 못 하면 옮기지 않음. (실험판: `experiments/hide-probe`, 확인표는 그 README.) 기존 👻(`is_system`) 숨김을 어떻게 이어받을지(그대로 두기/옮기기)와 SavePoint 없는 기기에서 숨김이 안 보이는 점은 그때 정함.
   - **결과(2026-11, 실험판 0.1.1, 실제 실리태번): ④에서 통과 못 함 → 지금 방식으로는 옮기지 않음.** ①은 통과(일반 전송·대신 쓰기에서 고른 원문만 정확히 빠짐, 숨김 표시 변화 없음). 그러나 채팅을 직접 읽어 장면 상태를 프롬프트에 넣는 다른 확장이, interceptor로 뺀 메시지의 내용을 그대로 다시 넣음. 같은 메시지를 `/hide`(`is_system`)로 숨기면 그 확장도 건너뜀. 즉 숨김 표시를 보고 판단하는 확장과는 "AI 요청에서만 빼기"가 맞지 않음(SavePoint가 고칠 수 없는 쪽). 따라서 하이드·🔶는 v0.7.0 뒤에도 채팅 파일의 숨김 표시를 쓰고, 쓰기는 `writeChatFile`(v0.6.8x 규칙)로만. 다시 검토하려면 숨김 표시와 같은 효과를 다른 확장에 줄 방법이 먼저 있어야 함.
3. **이어하기 #0 교체는 따로 판단** — 빈 방·인사말만 있는 방이라도 파일을 덮는 요청이 남으면 같은 경합이 남음. 방법(실리태번 자체 메시지 경로로 넣기, #0을 바꾸지 않고 주입으로 보여 주기 등)은 그때 비교.
- **용어:** 3번까지 분리되기 전에는 "채팅 파일 쓰기 0"이라고 부르지 않음(기억만 분리된 상태는 "기억 저장 분리").
- **나중에 (화면, 시안 먼저):** 👻 하이드 버튼을 자동 모드에서도 늘 보이게 하고 눌러서 바로 숨기기. 🔶 하이드 제외를 이름 옆에서 바로 끄기.
