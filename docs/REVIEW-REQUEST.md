# 설계 의견 요청 · 떼어 둔 작업 ②: 연결 보류된 방에 세이브 슬롯으로 기억 연결 (브랜치 `v0.7.4`, 코드 변경 전)

- 기준: `main` `983b726`(v0.7.3). **아직 코드는 없어요.** 아래 초안에 대한 설계 의견을 부탁해요(결과는 P1/P2/P3 또는 항목별 동의/반대로).
- 배경: v0.7.0부터 기억은 채팅 파일 밖의 기억 파일에 있어요. 방을 열 때 `decideRoom`(home.js)이 기억을 정하지 못하면 방은 `연결 보류`(held)가 되고 아무것도 저장하지 않아요. 지금 보류에서 빠져나오는 길은 둘뿐이에요: 이름 변경 이어서 연결(`carryRoom`, 5행)과 기억 복사 복구(`rescueRoom`, 8행 후보가 하나이고 기록 범위 원문이 모두 같을 때). 그 밖의 보류 방은 세이브 슬롯이 있어도 쓸 수 없어요(`loadSave`가 `gateOpen()`에서 거절).
- 겪은 사례: ① 채팅만 다른 설치로 가져온 방(기억 파일 없음 → 11행 `traces`), ② 실제 확인에서 본 "복구한 방 + 지운 원래 방 기록 = 후보 둘"(8행 `sameIntegrity`, 복구 버튼 없음).
- 지켜 온 방향(바꾸지 않음): 다른 방의 기억·이름표는 건드리지 않음(c4: 옮기지 않고 독립 사본) · 방이 지워졌는지 추정하지 않음 · 동의는 그 제안 하나에 묶음 · 쓰기 직전에 다시 읽음 · 서버에 "비교 후 쓰기"가 없어 짧은 틈은 남는다고 적음.

## 코드에서 확인한 것
1. 동의 → 다시 판정 → 쓰기의 틀이 이미 있어요: `carryRoom`·`rescueRoom`이 `h.agree`/`h.rescueAgree`를 걸고 `recheckHome('user')` → `linkRounds`가 `input.agreed`/`input.rescued`로 `decideRoom`에 넘김 → 판정이 그 동의와 지금 읽은 파일이 같을 때만 `rename`/`branch`를 냄 → `actHome`이 `placeMemory`로 씀.
2. `placeMemory`/`writePlan`은 있는 기억 파일을 다시 쓰지 않아요. 이름표가 이미 있으면 같은 연결(`sameLink`)일 때만 통과, 아니면 `tagChanged` 보류. 순서: 본체 → 다시 읽기 → 고유값 단서 → 이름표(마지막). 중간에 끊기면 다음 열기의 6행 `relink`가 본체는 두고 나머지만 이어 씀.
3. 갈래 판정(7행 `branchRestore`)은 이미 슬롯을 써요: 부모 방의 AUTO·QUICK 중 `pos.digest`가 이 방 원문 앞부분과 같은 슬롯 → `{ v: 1, mem, lastIndex, hashes: prints.slice(0, last + 1), history: [], floor: last, lootQueue: [] }`.
4. 슬롯 목록(index)에 `pos { lastIndex, digest }`가 들어 있어 파일을 읽지 않고도 이 방 원문과 맞는 슬롯을 고를 수 있어요(`metaOf`는 `mem`·`lastReply`만 뺌). 가져온 슬롯(`importSaves`)도 `pos`·`room`을 그대로 둬요.
5. 기억이 연결된 뒤 채팅 파일의 SavePoint 숨김이 기억의 기록 범위 밖에 있으면 `h2Of` → `hides`로 멈추고, `원문과 기억 맞추기`(`fitRoom`)가 그 숨김만 풀어요(c4 복구에서도 같은 경로: `RESCUE_TEXT.hides`). 복구 사본은 쓴 뒤 채팅 파일을 한 번 더 읽어 확인해요(`rescueCheck`, c4a P2).
6. `validFrom`(home.js 163)은 `from.kind`가 `migrate`·`branch`·`new`일 때만 통과시켜요. 새 종류(`slot`)를 넣으면 v0.7.3 이하에서 그 기억 파일이 "읽지 못함"이 돼요.
7. 두 기기가 같은 방에서 거의 동시에 서로 다른 슬롯을 골라도 쓰는 파일은 하나(`memName(homeId(addr, integrity))`)예요. `writeMem` 직전 다시 읽기와 `checkMem`(영수증)으로 대부분 한쪽이 멈추고, 틈으로 둘 다 지나가도 나중에 쓴 본체 하나만 남아요. 진 쪽 화면은 다음 저장에서 `canWrite` 불일치로 멈춰요(`MF_CONFLICT`). 기억이 둘로 갈리지는 않고, 진 쪽이 고른 슬롯은 그대로 남아요. (읽어서 확인, 검사로는 아직)

## 초안
**무엇:** 보류된 방에서 사용자가 세이브 슬롯 하나를 골라 동의하면, 그 슬롯의 기억으로 **이 방의 새 기억 파일**(`homeId(addr, integrity)`)을 만들고 연결해요. 다른 방의 기억·이름표·슬롯은 그대로.

### A. 어떤 보류에서 (범위)
- **1차(제안):** 이 이름에 이름표가 없고, 이 방 몫의 기억 파일·시작 표시·옮김 표시가 없고, 채팅 파일에 고유값이 있는 보류만: **`traces`(11행) · `sameIntegrity`(8행) · `parentGone`·`branchUnproven`(7행)**. 여기서는 `placeMemory`의 기존 갈래 쓰기를 그대로 쓸 수 있어요(새 쓰기 경로 없음).
- **1차에서 빼는 것:**
  - 이름표가 이미 있는 보류(`integrity`·`copyChanged`(2행)·`integrityGone`·`unproven`·`memGone`·`homeDiff`·`renamedAway`): 이름표를 바꿔 써야 해서 새 쓰기 경로가 필요하고, 그 이름표가 가리키는 기억이 다른 방 것일 수 있어요.
  - `renameUnproven`(5행): 예전 이름 쪽에 진짜 기억이 살아 있어요(이어서 연결이 먼저).
  - `copyMoved`(9행)·`movedNoBody`·`moveStarted`·6행의 보류들: 예전 사본 이전 표시와 얽혀요.
  - 고유값 없는 방: 기억 ID를 만들 수 없어요.
- 질문 A1: 1차 범위가 맞는지. `memGone`(이름표는 있는데 기억 파일이 없음)은 슬롯 복구가 가장 필요한 경우인데, 이름표 교체 없이 풀 방법이 있는지(예: 이름표가 가리키는 그 ID로 본체만 다시 만들기 — `writePlan`이 일부러 막아 둔 것).
- 질문 A2: `sameIntegrity`에서 슬롯 연결을 허용하면 "세 번째 복제본부터는 보류"라는 정한 방향을 사용자가 손으로 넘는 길이 돼요. 복구 사본과 같은 성격(독립 기억, 다른 방은 그대로)이라 괜찮다고 봤는데 맞는지.

### B. 어떤 슬롯을 (원문 맞추기)
- **1차(제안): 기록 위치가 이 방 원문과 정확히 맞는 슬롯만.** `pos.lastIndex < prints.length`이고 `digest(prints.slice(0, lastIndex + 1)) === pos.digest`. 방 이름은 보지 않아요(가져온 슬롯·이름 바꾼 방도 되게). 복사 복구와 같은 기준("기록한 원문이 모두 같음")이라 `source` 불일치가 생기지 않아요.
- 맞는 슬롯이 여럿이면 사용자가 고름(카드에 기록 범위·저장 시각 표시). 자동 선택 없음.
- 만든 상태: 7행 슬롯 경로와 같은 모양(`history: []`, `floor: last`) + `branchState`. 그 지점 이전으로 ⏪ 불가.
- **안 맞는 슬롯(원문이 달라졌거나 `pos` 없는 옛 슬롯)은 1차에서 연결 버튼 없음.** 허용하려면 기억만 붙이고 기록 범위를 비워야 하는데(`loadSave`의 `detachMem`, `lastIndex -1`), 그러면 이 방의 SavePoint 숨김이 전부 범위 밖 → `hides`로 멈춤 → 숨김을 다 풀어야 하고, 다음 세이브가 #0부터 다시 기록해 내용이 겹칠 수 있어요.
- 질문 B1: 정확히 맞는 슬롯만으로 시작하는 게 맞는지. 안 맞는 슬롯은 🟡(경고 문구와 함께 나중에) / ⚪ 중 어느 쪽인지.
- 질문 B2: 슬롯 위치 뒤(`lastIndex` 초과)에 남은 SavePoint 숨김은 기존 `hides` 멈춤 + `원문과 기억 맞추기`에 맡기면 되는지, 연결 전에 "숨김 N개가 풀려야 해요"를 미리 알려야 하는지.

### C. 동의와 쓰기
- 동의가 묶이는 것: 슬롯(`id`·`updated`·`pos`·기억 내용 해시) + 이 방(`addr`·`integrity`·예전 사본 해시·열기 `epoch`) + 보류 이유. `rescueAgree`와 같은 수명(이 열기의 다음 판정 한 번).
- 흐름: 버튼 → 슬롯 파일 읽기 → 확인창(슬롯 이름·기록 범위·저장 시각, "이 방에 새 기억을 만들어요. 다른 방의 기억은 그대로") → `recheckHome('user')` → `decideRoom`이 같은 행에서 보류 대신, 동의와 지금 읽은 파일·원문이 같을 때만 `branch`(via `slotPick`)를 냄 → `placeMemory`(갈래 쓰기) → `rescueCheck`처럼 쓴 뒤 채팅 파일을 다시 읽어 확인 → `h2Of`.
- `from`은 새 종류를 만들지 않고 `{ kind: 'branch', addr, integrity, slot: <id> }`(부모 없음)로. v0.7.3 이하에서도 읽혀요.
- 슬롯 내용을 `decideRoom`에 넘기는 방법: `input.slotted`에 내용까지(순수 함수 유지) vs `slotsOf`처럼 읽기 함수로.
- 질문 C1: `from`을 `branch`로 두는 것(코드 6). 6행 `relink`·`checkMem`의 `from` 비교(`canon`)에 슬롯 ID가 들어가서, 두 기기가 다른 슬롯을 고르면 `otherOrigin`으로 멈추는 게 의도예요.
- 질문 C2: 8행은 판정 순서가 7행보다 앞이에요. `sameIntegrity` 보류 방에서 슬롯 동의가 있으면 8행에서 바로 `branch`를 내도 되는지(후보 방들의 기억은 읽지도 쓰지도 않음).
- 질문 C3: 두 기기 동시 선택(코드 7)이 지금 방식으로 충분한지, 추가 장치가 필요한지.

### D. 화면
- 보류 안내 문구에 한 줄("이 방 원문과 맞는 세이브 슬롯이 N개 있어요. 세이브 탭에서 `이 방에 연결`로 기억을 붙일 수 있어요"), 세이브 탭의 맞는 슬롯 카드에 `이 방에 연결` 버튼(보류 + 1차 범위일 때만). 보류 상세(`자세히 보기`)의 "할 수 있는 일"에도 같은 줄.
- 맞는 슬롯 계산은 목록(index)의 `pos`와 판정 때 읽은 원문 지문으로(추가 읽기 0).
- `loadSave`의 보류 거절은 그대로(불러오기와 연결은 다른 버튼).

### 안 하려는 것 (⚪)
- 맞는 슬롯 자동 연결(동의 없이) · 슬롯으로 다른 방 기억 덮기 · 방이 지워졌는지 채팅 목록으로 추정 · 보류 판정 자체를 느슨하게 바꾸기.
