## 정한 기준 (그대로 봐 주세요)

- **P2-1:** 성공 응답을 받은 사본은 바로 삭제 비교 기준(v0.6.83 그대로). 단, **그 요청을 보낸 뒤 이 화면에서 지운 기록**은 새 기준에서도 남김.
- **P2-2:** 기억 없는 방에서 파일이 보낸 사본들과 다르면, 이번 작업이 바꾼 표시를 메시지마다 파일에서 확인. 같은 자리·같은 메시지·같은 스와이프인지 먼저 보고, 모두 직후 값이면 유지, 모두 변경 전 값이면 되돌림, 그 밖(자리·메시지가 바뀜, 일부만)은 **보류**(되돌리지 않고 확인 대기). 🔶를 끈 작업은 "표시 없음"이 반영된 결과.
- **P3:** 200이어도 실리태번의 성공 응답(`{ ok: true }`, 1.12.x 이전 `{ result: 'ok' }`)이 아니면 응답 없음(방 멈춤).
- **P1:** 이어하기 뒤 첫 메시지는 **화면만** 그림(`updateMessageBlock` / 빈 화면이면 `addOneMessage`). `reloadCurrentChat`·`clearChat`은 쓰지 않음.
- **P2-4:** 첫 메시지를 실제로 되돌렸을 때만 `tainted`도 되돌림. 남겼으면 안내에 그 사실을 씀.
- **P2-3:** AUTO는 저장이 확인된 순간 만든 슬롯(기억 + 마지막 답변)을 타이머가 그대로 저장. 타이머는 화면을 다시 읽지 않음.
- **합의한 한계(고치지 않음, 그대로):** 방을 다시 열거나 새로고침한 뒤 늦은 요청이 도착하는 경우. 그사이 실리태번 자체 저장이 늦은 요청에 잠깐 덮이는 경우(화면엔 남음). 보류해 둔 "방 이동 뒤 늦은 저장" 열린 문제.

## 특히 봐 줄 곳

### v0.6.85 (저장 쪽)
1. `seenSent`: 지운 기록을 차례 번호(`delTick`)로 남기고, 요청 뒤 삭제만 새 기준의 `cut`으로. 요청 전에 지운 것은 보낸 사본에 이미 반영된 것으로 봐요. 이 구분이 틀리는 순서가 있는지(다른 기기 삭제를 놓치는 쪽 포함).
2. `marksInFile`: "같은 메시지"를 SavePoint 표시를 뺀 해시로 봐요. 그 메시지에 번역이 붙으면 보류(방 멈춤)로 가요. 반대로 같은 해시인데 다른 메시지로 보는 경우가 있는지, `changedMarks`가 쓰기 직후 자리로 잡는 게 실제 보낸 사본과 어긋나는 순서가 있는지(같은 작업 안의 재전송 포함).
3. 성공 응답 모양 확인: 실리태번 버전별로 다른 모양이 더 있는지. 있다면 저장마다 방이 멈춰요(덮지는 않음).

### v0.6.86 (동작)
4. `showCarried`: 빈 화면 판단(`#chat .mes`가 하나도 없음). 실리태번에서 이어하기 직후 화면에 다른 메시지 요소가 남아 있는 경우가 있는지, 그때 첫 메시지가 안 보이는 것 말고 더 나쁜 결과가 있는지.
5. `autosave`: 타이머가 돌 때 방을 옮겼어도 확인된 슬롯은 저장해요(예전엔 건너뜀). 슬롯 정리(`keepRooms`)나 QUICK과 섞이는 문제가 있는지.
6. 이어하기 거절 안내 두 갈래(오류 안내 / 방 멈춤일 때 따로 알림)가 실제 화면에서 겹치거나 모순되는지.

### 문서
7. `docs/PLAN-v0.7.md` v0.7.0 합격 기준 11번(기억 파일 쓰기끼리 순서 뒤집힘). 빠진 경우가 있는지.

- `save-pending.cjs`의 `answer(ev, n, how)`: n번째 채팅 저장을 `'late'`(응답 없이 나중에 도착), `'cut'`(도착 후 응답 유실), 숫자(도착 후 그 상태로 답, `body` 지정)로.
