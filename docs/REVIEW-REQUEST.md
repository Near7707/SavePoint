## 무엇을 알아보려는 실험인가

`docs/PLAN-v0.7.md` 끝 "그 뒤" 2단계: 하이드를 채팅 파일의 `is_system` 대신 **AI 요청에서만 빼는 방식**(`generate_interceptor`)으로 옮길 수 있는지. v0.7.0(기억 저장 분리)보다 먼저 확인하기로 했어요. 결과에 따라 기억과 숨김을 한 파일에 같이 둘지 정해요.

이 실험이 보는 것은 **"새 방에서 고른 메시지만 정확히 빠지는가"**뿐이에요. "지금 쓰는 방(예전 `is_system` 숨김, 분기방)을 그대로 이어 쓸 수 있는가"는 따로 설계 검토해요.

## 정한 기준 (그대로 봐 주세요)

- 채팅 파일을 쓰지 않고 `is_system`도 바꾸지 않음. 고른 메시지 목록은 확장 설정(`settings.json`)에.
- 메시지는 번호가 아니라 (보낸 시각·이름·사용자 여부 + 글 지문)으로 기억.
- 요청 목록과는 **순서대로 짝 맞춤**: 같은 `extra` 객체면 확실, 아니면 방 안에서 유일한 (시각·이름·사용자)일 때만. 확실하지 않으면 **빼지 않고 남김**(잘못 빼는 것보다 남기는 쪽).
- 이미 숨긴 메시지, 스와이프로 빠진 마지막, 이어쓰기 대상은 빼지 않고 이유를 기록.

## 특히 봐 줄 곳

1. `probe-core.js`의 `pairCore`: 실리태번 1.19 `Generate`(`public/script.js`의 `coreChat` 만들기 ~ `runGenerationInterceptors`)와 비교해서, **엉뚱한 메시지를 빼는 순서**가 있는지. 특히 도구 호출(`tool_invocations`)이 붙은 `is_system` 메시지가 목록에 남는 경우, 다른 확장의 interceptor가 항목을 바꾸거나 복사하는 경우.
2. `findMarked`: 메시지를 고친 뒤, 스와이프를 바꾼 뒤, 앞쪽을 지운 뒤에 다른 메시지를 가리키는 경우가 있는지.
3. interceptor를 거치지 않는 요청 경로가 더 있는지. 지금 아는 것: 프롬프트 관리자 토큰 계산(`dryRun`), 매크로(`{{lastMessage}}` 등), 채팅을 직접 읽는 다른 확장. 실제 요청 중에 빠지는 경로(예: 조용한 생성, 그룹 자동 진행, 다른 API 종류)가 있으면 알려 주세요.
4. `experiments/hide-probe/README.md`의 확인표 9칸에 빠진 경우가 있는지.
