## 사용자 결정 (그대로 봐 주세요)

- **실리태번 저장 가로채기(쓰기 순서 공유)는 보류.** 같은 기기에서 이미 출발한 SavePoint 요청이 실리태번의 더 새 저장보다 늦게 도착하고 그사이 방을 옮기면 원래 방의 최신 대화가 빠지는 문제(지난 리뷰 P1 ①)는 **열린 문제**로 README·REVIEW.md에 적었어요. 이 경우를 고쳤는지가 아니라, 이번 수정이 이 틈을 **더 넓히지 않았는지** 봐 주세요.
- 눈 버튼으로 펼친 원문이 자동 하이드에서 다음 저장 때 다시 숨겨지는 동작은 그대로 두고 README 문구만 맞췄어요.

## 특히 봐 줄 곳

### v0.6.76 (저장 쪽, 가장 중요)
1. `writeEntry`·`guardedSave`가 실리태번 저장(`stIdle`)을 **서버 확인 전에** 기다리는지, 확인 → 적용 → 보내기 사이에 기다림이 남은 곳이 없는지.
2. `writeChatFile`이 기다렸거나 다시 보낼 때 `fileAllows`로 서버를 읽는 규칙: 화면이 파일을 덮거나, **방금 이 화면이 보낸 사본이 파일을 덮으면** 다시 보냄. 두 번째 조건(내 예전 사본이 실리태번의 새 저장보다 늦게 도착한 경우)이 다른 기기의 변경을 놓치는 경우가 있는지. 다른 곳에서 지운 메시지(`gone`)는 두 번째 조건으로 통과시키지 않아요.
3. 첫 저장이 들어간 뒤의 오류(`landed`) → `settleLanded`: 서버에 이번 쓰기의 영수증(`proofOf`)이 있고 화면(또는 보낸 사본)이 파일을 덮으면 성공, 있지만 남의 내용이 있으면 방 막음, 못 읽거나 없으면 `markUnsure`. 화면은 어느 경우에도 되돌리지 않음. 이 판단이 맞지 않는 순서가 있는지.
4. `landed`에는 "기다리는 동안 실리태번이 변경이 들어간 화면을 저장했을 수 있음"도 포함해요. 이 경우 첫 요청 전 실패도 되돌리지 않아요. 지나치게 넓은지.
5. 네 번 돌 동안 한 번도 못 보내면(실리태번 저장이 계속 이어짐) 이제 오류로 끝나요(예전에는 조용히 성공 처리). 평소에 이 오류가 날 수 있는지.

### v0.6.77 (하이드)
6. 하이드 스냅샷을 모든 변경에서 잡도록 한 뒤, 되돌릴 때 `syncHide`를 다시 부르지 않는 것이 문제를 만드는 경로가 있는지(예: 실패한 변경 전에 화면이 이미 어긋나 있던 경우).
7. 되돌릴 때 화면 표시를 메시지의 **지금 위치**로 칠하는 것(저장이 가는 사이 지워진 메시지는 건너뜀). 스냅샷 뒤에 끼어든 새 메시지는 손대지 않아요.

### v0.6.78 (`home.js`)
8. `writeTag` 직전 다시 읽기: 없음 → 씀, 같은 연결(기억ID·고유값 같음) → 그대로 완료, 그 밖 → `tagChanged` 보류, 손상·오류 → 멈춤. 처음 이전에도 적용돼요. "같은 연결"에서 빠진 조건이 있는지.

### v0.6.79 (화면)
9. 기억 없는 방에서 주입 계산 열쇠를 비우는 것이 다른 탭·다시 열기에서 계산을 쓸데없이 다시 하게 만드는지.
10. 전원 버튼 hover 그림자를 없애는 규칙(`.sp-power .sp-btn.sp-power-btn:hover`)이 다른 스킨의 의도된 표시를 막는지.

- 리뷰 ②·③ 재현에 쓴 손잡이: `M.stScript.setChatSaving(true/false)`(실리태번 저장 중), `M.metaDelay`(SavePoint 요청 지연), `M.beforeChatSave`(요청이 서버에 닿기 직전), `M.readDelayFor = { 파일: ms }`(다시 보내기 전 읽기를 늦춰 그 사이 다른 기기 쓰기를 끼워 넣음), `M.serverFiles[이름].push(…)`(다른 기기), `M.failNth`·`M.failOnce`, `M.serverError`.
