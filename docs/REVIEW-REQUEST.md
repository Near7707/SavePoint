## 바뀐 것
- **P1 조건부 다시 보내기:** 공통 저장기(`writeChatFile`)의 두 번째 `guard` 호출이 `{ sent, file }`(그 라운드에 읽은 파일)를 받아요. 보낸 뒤 `guard`가 `'stop'`을 돌려주면 더 보내지 않고 `fitHeld` 오류로 끝나요. 이 값을 쓰는 건 맞추기뿐이에요.
- 맞추기는 다시 보내기 전에 영수증(`fitOk`), 방금 읽은 파일과 화면의 숨김 상태 전부(푼 대상 포함), 🔖가 같아야 다시 보내요. 아니면 멈추고, 이미 들어간 숨김 풀기는 그대로 두고, 방은 멈춘 채, 화면에만 메시지가 있으면 복사 안내를 붙여요. 성공 안내는 없어요.
- **P2-1:** `keepSame` — 메시지와 스와이프의 🔖만 비교해요(HELD·VISIBLE·LIVE는 안 봄). 차례의 읽기, 첫 요청, 다시 보내기 모두에서요. 공용 비교 사본은 안 건드렸어요.
- **P2-2:** `fitEnd`는 마지막 읽은 파일의 고유값이 화면과 같고 `fileBase`를 통과할 때만 H2를 풀어요. 쓰기 0("이미 맞음") 경로도 같아요. 아니면 멈춘 채 안내해요.

## 특히 봐 줄 곳
1. `'stop'`은 보낸 뒤에만 써요. 첫 요청 전에는 예전처럼 `false` → `nothingSent` → 되돌림이에요. 이 나눔이 맞는지, 다른 저장의 `guard`에 영향이 없는지.
2. 멈춘 뒤 서버 파일에는 실리태번이 먼저 저장한 새 메시지가 빠져 있을 수 있어요(첫 요청이 덮은 경우). 화면에만 남고 복사 안내만 해요. 방이 H2로 멈춰 있어서 우리는 더 쓰지 않는데, 실리태번 자신의 다음 저장이 그 메시지를 다시 넣는 것에 기대도 되는지.
3. 멈춘 뒤 `gate.seen`은 방금 읽은 파일(다른 탭의 직접 숨김·🔖가 있는 파일)이에요. 화면은 그 숨김·🔖가 없는 상태라, 다시 열기 전까지 이 화면과 파일이 다른 채로 남아요. 방은 H2라 쓰지 않지만, 문제가 될 경로가 있는지.
4. 스와이프 🔖 비교는 지금은 겹 장치예요(스와이프 `extra`는 채팅 비교에 들어가서 `serverCovered`가 먼저 막음, 24 둘째 줄은 고치기 전 코드도 통과).
5. 재개 조건에서 고유값을 `fileBase`와 별도로 봐요(파일에 고유값이 없는 경우까지). 너무 엄격하지 않은지.
