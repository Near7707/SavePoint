## 정한 기준 (그대로 봐 주세요)

- **P1-1:** 같은 방에서 성공 응답을 받은 사본은 받는 즉시 삭제 비교 기준(`gate.seen`).
- **P1-2:** 파일에 내용이 들어갔는지와 요청이 끝났는지를 나눔. 응답이 끊긴 요청이 있으면 파일에 같은 사본이 보여도(실리태번도 화면을 통째로 저장하므로) 그 방의 **다음 SavePoint 저장을 보내지 않음**(`gate.pending`, 방을 다시 열거나 새로고침할 때만 풀림). 이번 패치의 완료 기준이에요.
- **500:** 실리태번 저장 처리가 직접 보낸 500(그 catch 문장과 정확히 같음)만 끝난 요청으로 보고 파일을 다시 읽어 판단. 다른 500·408·502·503·504는 응답 끊김과 같음. 고유값 거절(400)은 그 요청이 쓰기 전에 막힌 것.
- **되돌림:** 그 작업이 바꾼 내용이 파일에 반영되지 않았다고 확인됐을 때만(파일을 읽었고, 변경이 없고, 그 작업의 요청이 더 도착할 수 없음). SavePoint 요청이 모두 거절돼도 실리태번 자체 저장이 변경을 먼저 넣었으면 화면 유지. 첫 저장이 성공하고 재전송만 실패하면 첫 변경 유지.
- **합의한 한계(고치지 않음):** 방을 다시 열거나 새로고침한 뒤 늦은 요청이 도착하는 경우. 그사이 실리태번 자체 저장이 늦은 요청에 잠깐 덮이는 경우(화면엔 남음). 보류해 둔 "방 이동 뒤 늦은 저장" 열린 문제.

## 특히 봐 줄 곳

### v0.6.83 (저장 쪽, 가장 중요)
1. 성공 응답 직후 `setSeen(tSnap)`. 이때 `gate.cut`이 비워져요. 요청이 가는 사이 이 화면에서 지운 메시지가 "다른 곳에서 지운 것"으로 잘못 잡히거나, 반대로 다른 기기 삭제를 놓치는 순서가 있는지.
2. `gate.pending`이 막는 범위: `gateOpen()`이 거짓이 되어 `transact`·`guardedSave`·체크포인트·QUICK이 모두 보내지 않아요. `writeEntry`는 맨 앞에서 거절. 응답 없는 요청 뒤에 SavePoint 저장이 나갈 수 있는 경로가 남았는지(다른 채팅 파일 쓰기 경로, 같은 작업 안의 다음 라운드 포함).
3. `settleWrite`: 모든 실패를 파일을 읽어 판단해요. 되돌림 조건이 "파일과 완전히 예전 그대로"에서 "파일을 읽었고 이번 변경이 없음 + 더 도착할 요청 없음"으로 바뀌었어요(고유값 거절처럼 파일이 아예 다른 경우 포함). 이 조건에서 파일에 반영된 변경을 되돌리는 경우가 있는지. 파일을 못 읽으면 되돌리지 않고 "확인 못 함".
4. `holdsWrite`의 `copies`(쓰기 직전 화면 + 실제로 보낸 사본 전부). 기억 없는 방에서 남의 저장을 내 것으로 잘못 보는 순서가 있는지.
5. "성공 응답 = 파일에 씀" 전제(확인한 실리태번은 쓰기 오류를 삼키지 않음). 이 전제가 깨지는 경우가 실제로 있는지, 있다면 방이 잘못 멈추는 것 말고 더 나쁜 결과가 있는지.
6. 실리태번 500 구분을 오류 문장으로 하는 것. 확인한 실리태번 버전 밖에서 문장이 다르면 방 멈춤 쪽으로 가요.
